# NFR 要件

このドキュメントでは、「スヌーズを押せ」アプリケーションの非機能要件を定義します。

**軽量化方針**: `aidlc-docs/inception/requirements/requirements.md` の「2. 非機能要件」に記載済みの内容を最大限再利用し、実装のために追加で必要な事項のみを定義します。

---

## 1. 既存 NFR の参照

以下の非機能要件は既に定義されています：

**参照**: [`aidlc-docs/inception/requirements/requirements.md` の「2. 非機能要件」](../../inception/requirements/requirements.md#2-非機能要件)

### 既定義の NFR サマリー
- **パフォーマンス**: AI メッセージ生成 5 秒以内、アラーム鳴動 1 秒以内、UI レスポンス 1 秒以内
- **コスト**: ハッカソン期間 $1 以下、Nova Lite → Claude Haiku/Sonnet、max_tokens: 200
- **セキュリティ**: 認証なし、HTTPS、API キー非露出、API Gateway + Lambda 経由で Bedrock 呼び出し
- **ブラウザ対応**: Chrome/Safari 最新版、レスポンシブデザイン
- **可用性**: オフライン対応、ローカルストレージで基本機能動作
- **スケーラビリティ**: サーバレス自動スケール、DynamoDB オンデマンド
- **保守性**: マネージドサービス、IaC、可読性

## 2. 実装に必要な追加 NFR 詳細

### 2.1 パフォーマンス詳細

#### タイムアウト設定
- **Bedrock API タイムアウト**: 10 秒
  - 理由: 要件は 5 秒以内だが、余裕を持たせてフォールバックの機会を確保
  - フォールバック: タイムアウト時はデフォルトメッセージを表示
- **Lambda 関数タイムアウト**: 30 秒
  - 理由: Bedrock 呼び出し + 処理時間を考慮した標準設定
- **フロントエンド API 呼び出しタイムアウト**: 15 秒
  - 理由: Lambda タイムアウト + ネットワーク遅延を考慮

#### リトライ戦略
- **フロントエンド → API Gateway**: 1 回リトライ
  - 理由: ネットワークエラーの一時的な回復を期待
  - リトライ間隔: 1 秒
  - 失敗時: フォールバックメッセージを表示
- **Lambda → Bedrock**: リトライなし
  - 理由: タイムアウトで十分な時間を確保済み
  - 失敗時: デフォルトメッセージを返す

#### キャッシュ戦略
- **メッセージキャッシュ**: なし
  - 理由: 毎回新しいメッセージを生成することが体験の価値
- **設定キャッシュ**: ローカルストレージ
  - 理由: オフライン対応、高速読み込み

### 2.2 コスト詳細

#### Lambda 設定
- **メモリ**: 256 MB
  - 理由: Bedrock SDK の動作に十分、コストとパフォーマンスのバランス
- **アーキテクチャ**: x86_64
  - 理由: 標準、互換性重視

#### DynamoDB 設定
- **キャパシティモード**: オンデマンド
  - 理由: ハッカソン期間のトラフィック予測不要、自動スケール
- **テーブル**: SnoozeRecords のみ（AlarmConfigs は将来用のためスキップ）
  - 理由: MVP では認証なし、ローカルストレージで設定管理

#### Bedrock モデル選択
- **開発時**: Amazon Nova Lite
  - 理由: 低コスト、開発・テスト用
- **本番デモ時**: Claude Haiku
  - 理由: バランス型、品質とコストの両立
- **max_tokens**: 200（全リクエスト）
  - 理由: 120 字以内のメッセージ生成に十分

### 2.3 セキュリティ詳細

#### API Gateway 設定
- **認証方式**: 認証なし
  - 理由: MVP 方針、ユーザー登録なし
- **CORS 設定**: すべてのオリジンを許可
  - 理由: 開発・デモ用、ハッカソン期間のみ
  - 本番化時: Amplify Hosting ドメインのみに制限

#### 環境変数管理
- **方法**: Lambda 環境変数
  - 理由: シンプル、ハッカソン MVP に十分
- **保存内容**: Bedrock モデル ID、リージョン、タイムアウト値
- **機密情報**: なし（IAM ロールで Bedrock アクセス制御）

#### データ保護
- **ローカルストレージ**: 暗号化なし
  - 理由: 個人情報なし、機密情報なし
- **DynamoDB**: 暗号化有効化（デフォルト）
  - 理由: AWS ベストプラクティス
- **通信**: HTTPS のみ
  - 理由: API Gateway、Amplify Hosting のデフォルト

### 2.4 監視・ログ詳細

#### CloudWatch Logs
- **保持期間**: 7 日
  - 理由: デバッグ可能、コスト抑制
- **ログレベル**: INFO
  - 理由: 標準、エラーと主要イベントを記録
- **ログ内容**:
  - Lambda 関数の開始・終了
  - Bedrock API 呼び出しの成功・失敗
  - エラーメッセージとスタックトレース

#### エラー通知
- **方法**: なし
  - 理由: ハッカソン MVP では不要、CloudWatch Logs で手動確認
- **本番化時**: CloudWatch Alarms + SNS を検討

#### メトリクス
- **Lambda メトリクス**: 実行時間、エラー率、同時実行数（CloudWatch 自動収集）
- **API Gateway メトリクス**: リクエスト数、レイテンシ、エラー率（CloudWatch 自動収集）
- **カスタムメトリクス**: なし
  - 理由: ハッカソン MVP では不要

### 2.5 データ管理詳細

#### ローカルストレージ
- **データ構造**: JSON 形式
  - 理由: シンプル、可読性高い、デバッグ容易
- **保存内容**:
  - アラーム設定（時刻、有効/無効、スヌーズ間隔）
  - スヌーズ記録（日付、回数、連続日数）
  - 堕落ゲージ値
- **容量制限**: 5 MB 以下を想定
  - 理由: ブラウザのローカルストレージ制限を考慮

#### DynamoDB
- **テーブル**: SnoozeRecords
  - Partition Key: `userId` (String)
  - Sort Key: `timestamp` (String, ISO 8601)
  - 属性: `action`, `messageId`, `pattern`
- **データ同期**: オンライン復帰時のみ
  - 理由: オフライン優先、バッテリー節約
  - 同期タイミング: ページロード時、オンラインイベント時

#### データ保持
- **ローカルストレージ**: 無期限（ユーザーが削除するまで）
- **DynamoDB**: 無期限（ハッカソン期間後に手動削除）

### 2.6 ブラウザ対応詳細

#### 対応ブラウザ
- **Chrome**: 最新版（バージョン 120+）
- **Safari**: 最新版（バージョン 17+）
- **Edge**: 最新版（Chromium ベース）
- **Firefox**: 対応外（ハッカソン MVP では優先度低）

#### 必要な Web API
- **Notification API**: アラーム通知
- **Audio API**: 音声アラート、雨音 BGM（Nice-to-have）
- **localStorage API**: データ永続化
- **fetch API**: API 呼び出し

#### レスポンシブデザイン
- **ブレークポイント**:
  - モバイル: 〜768px
  - タブレット: 769px〜1024px
  - デスクトップ: 1025px〜
- **優先**: モバイルファースト
  - 理由: 審査員がスマホでデモを見る可能性

### 2.7 可用性詳細

#### オフライン対応
- **基本機能**: ローカルストレージで動作
  - アラーム設定
  - アラーム鳴動（ローカルタイマー）
  - スヌーズ記録（ローカル保存）
- **制限機能**: AI メッセージ生成（オンライン必須）
  - フォールバック: デフォルトメッセージを表示

#### エラーハンドリング
- **ネットワークエラー**: フォールバックメッセージ表示
- **Bedrock API エラー**: デフォルトメッセージ表示
- **DynamoDB エラー**: ローカルストレージのみで動作継続
- **予期しないエラー**: Error Boundary でキャッチ、エラー画面表示

#### フォールバックメッセージ
```
「雨音が聞こえます。今朝の世界は、あなたを必要としていません。」
「もう少しだけ、夢の中で。」
「今日の予定、全部明日でも大丈夫です。」
```

## 3. NFR 検証方法

### 3.1 パフォーマンステスト
- **AI メッセージ生成**: 10 回実行し、平均レスポンスタイムを測定
- **アラーム鳴動**: 設定時刻との誤差を測定
- **UI レスポンス**: ボタン押下から画面遷移までの時間を測定

### 3.2 コストモニタリング
- **AWS Cost Explorer**: 日次コストを確認
- **目標**: ハッカソン期間（30 日）で $1 以下

### 3.3 セキュリティチェック
- **HTTPS 通信**: ブラウザの開発者ツールで確認
- **API キー非露出**: フロントエンドコードに API キーがないことを確認
- **CORS 設定**: 異なるオリジンからのアクセスをテスト

### 3.4 ブラウザ互換性テスト
- **Chrome**: デスクトップとモバイルでテスト
- **Safari**: iOS でテスト
- **レスポンシブ**: 各ブレークポイントでレイアウトを確認

### 3.5 可用性テスト
- **オフライン**: ネットワークを切断して基本機能をテスト
- **エラーハンドリング**: 意図的にエラーを発生させてフォールバックを確認

## 4. NFR 優先順位

### 高優先度（必達）
- パフォーマンス（AI 5 秒、アラーム 1 秒、UI 1 秒）
- コスト（$1 以下）
- セキュリティ（HTTPS、API キー非露出）
- ブラウザ対応（Chrome、Safari）

### 中優先度（重要）
- 可用性（オフライン対応）
- 監視・ログ（CloudWatch Logs）
- エラーハンドリング（フォールバック）

### 低優先度（Nice-to-have）
- エラー通知（CloudWatch Alarms）
- カスタムメトリクス
- Firefox 対応
