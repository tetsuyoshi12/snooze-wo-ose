# アプリケーション設計計画

## 目的
高レベルのコンポーネント識別とサービスレイヤー設計を行う。

**注意**: 詳細なビジネスロジック設計は後の機能設計（CONSTRUCTION フェーズ）で行います。

## 前提条件
- ワークスペース検出完了
- 要件分析完了（機能コンテキストを提供）
- ユーザーストーリー完了（ユーザーストーリーが設計決定を導く）
- 実行計画でアプリケーション設計ステージの実行が指示されている

### ステップ 4: コンテキストに適した質問の生成

**指示**: 要件とストーリーを分析して、**この特定の**アプリケーション設計に関連する質問を生成します。以下のカテゴリをガイダンスとして使用します。各カテゴリを評価し、疑問がある場合は質問してください — 過信は悪い結果につながります。

- [Answer]: タグ形式を使用して質問を埋め込む
- 曖昧さ、欠落情報、明確化が必要な領域に焦点を当てる
- ユーザー入力が設計決定を改善する場所で質問を生成
- **疑問がある場合は質問する** - 過信は悪い設計につながる

**評価する質問カテゴリ**（すべてのカテゴリを考慮）：
- **コンポーネント識別** - コンポーネント境界、組織、グループ化戦略について質問
- **コンポーネントメソッド** - メソッドシグネチャ、入出力期待値、インターフェース契約について質問（詳細なビジネスルールは後で）
- **サービスレイヤー設計** - サービスオーケストレーション、境界、調整パターンについて質問
- **コンポーネント依存関係** - 通信パターン、依存関係管理、結合の懸念について質問
- **設計パターン** - アーキテクチャスタイルの好み、パターン選択、設計制約について質問

- [ ] すべての [Answer]: タグが完了するまで進まない
- [ ] ドキュメントを確認して [Answer]: タグが空白でないことを確認

### ステップ 8: 回答の分析（必須）
進む前に、すべてのユーザー回答を以下の点で注意深く確認する必要があります：
- **曖昧または不明確な回答**: "mix of"、"somewhere between"、"not sure"、"depends"
- **未定義の基準または用語**: 明確な定義のない概念への参照
- **矛盾する回答**: 互いに矛盾する回答
- **設計詳細の欠落**: 特定のガイダンスが欠けている回答

### ステップ 9: 必須フォローアップ質問
ステップ 8 の分析で曖昧な回答が明らかになった場合、以下を行う必要があります：
- [Answer]: タグを使用して明確化質問ファイルを作成
- すべての曖昧さが完全に解決されるまで承認に進まない
- **重要**: 徹底的に - すべての不明確な回答についてフォローアップ質問をする

## 重要なルール

### 計画フェーズのルール
- **コンテキストに適した質問**: この特定のコンテキストに関連する質問のみを尋ねる
- **必須回答分析**: 進む前に常に曖昧さの回答を分析
- **曖昧さを持って進まない**: 生成前にすべての曖昧な回答を解決する必要がある
- **明示的承認が必要**: 生成開始前にユーザーが計画を承認する必要がある

### 生成フェーズのルール
- **ハードコードされたロジックなし**: 設計計画に書かれていることのみを実行
- **計画に正確に従う**: ステップシーケンスから逸脱しない
- **チェックボックスを更新**: 各ステップ完了後すぐに [x] をマーク
- **承認された方法論を使用**: 計画からの設計アプローチに従う
- **完了を検証**: 次のステージに進む前にすべての設計成果物が完了していることを確認

### 完了基準
- すべての計画質問が回答され、曖昧さが解決されている
- 設計計画がユーザーによって明示的に承認されている
- 設計計画のすべてのステップが [x] としてマークされている
- 計画に従ってすべての設計成果物が生成されている（components.md、component-methods.md、services.md、component-dependency.md、application-design.md）
- 生成された設計がユーザーによって明示的に承認されている
- 設計が検証され、次のステージの準備ができている
