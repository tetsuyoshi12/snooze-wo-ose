# 要件定義書

## インテント分析サマリー

### ユーザーリクエスト
「スヌーズを押せ」という Web アプリケーションを greenfield で開発する。これは目覚ましアプリの形をした「朝起きられない人を生産する」サービスである。

### リクエストタイプ
新規機能開発（New Feature - Greenfield）

### スコープ推定
複数コンポーネント（Multiple Components）
- フロントエンド（React/Next.js）
- バックエンド API（Lambda + API Gateway）
- AI メッセージ生成（Bedrock）
- データ永続化（DynamoDB）
- 静的ホスティング（Amplify/CloudFront）

### 複雑度推定
中程度（Moderate）
- サーバレスアーキテクチャの統合
- AI プロンプト設計と複数パターンの実装
- リアルタイムアラーム機能
- ゲーミフィケーション要素（堕落ゲージ、連続記録、称号システム）

## 1. 機能要件

### 1.1 MVP 機能（ハッカソン必達）

#### F-01: アラーム時刻設定
- **説明**: ユーザーが 1 つの時刻を設定・保存できる
- **受入基準**:
  - 時刻選択 UI が提供される
  - 設定した時刻がローカルストレージに保存される
  - 設定内容が画面に表示される

#### F-02: アラーム鳴動
- **説明**: 設定時刻にブラウザ通知と音で発火する
- **受入基準**:
  - 設定時刻になるとアラームが鳴る
  - ブラウザ通知が表示される
  - 音声アラートが再生される
  - アラーム画面が自動的に表示される
  - スヌーズ間隔: デフォルト 5 分（設定可能）

#### F-03: AI メッセージ生成
- **説明**: Amazon Bedrock を呼び出し、5 パターンから 1 つを生成して表示
- **受入基準**:
  - 5 つのパターン（詩的、季節、屁理屈、共犯、科学）から 1 つが選ばれる
  - Bedrock API が呼ばれ、120 字以内の日本語メッセージが生成される
  - 生成されたメッセージが墨絵風 UI に表示される
  - レスポンスタイムは 5 秒以内

##### 5 つのメッセージパターン

| 種別 | 概要 | 例 |
|---|---|---|
| 詩的・文学的 | 比喩や情景描写で誘う | 「雨の音が聞こえます。今朝の世界はあなたを必要としていません」 |
| 季節の言葉 | 季語や二十四節気で誘う | 「立冬を過ぎました。冬眠の季節です」 |
| 屁理屈・駄目押し | 冷静に理屈で寝かしつける | 「今日の予定、全部明日でも大丈夫です」 |
| 共犯・同調 | 一緒に寝ようと誘い込む | 「私も眠いです。布団の中で会議しましょう」 |
| 科学的根拠 | 長時間睡眠の科学的メリット | 「7 時間以上の睡眠で記憶力が向上します」 |

#### F-04: 巨大スヌーズ UI（誘惑装置）
- **説明**: 画面の 8 割を占めるスヌーズボタンと、隅に小さい「起きる」ボタン。
  ユーザーが反射的にスヌーズを押すよう、UI が積極的に二度寝を誘導する。
- **設計意図**: 起きるかスヌーズかは"対等な選択肢"ではない。
  本作では明確にスヌーズを推奨する立場を取る。
- **受入基準**:
  - 「もう少し…」ボタンが画面の大部分（80% 以上）を占める
  - 「起きる」ボタンは隅に小さく配置されるが、押下可能
  - タップ/クリックで適切に反応する

#### F-05: スヌーズ記録
- **説明**: スヌーズ押下回数を保存
- **受入基準**:
  - スヌーズボタン押下時に回数がカウントされる
  - ローカルストレージまたは DynamoDB に保存される
  - 記録が永続化される

#### F-06: 堕落ゲージ表示
- **説明**: スヌーズ回数を可視化
- **受入基準**:
  - スヌーズ回数に応じてゲージが増加する
  - 視覚的に「堕落度」が分かる表示
  - 現在の堕落レベルが表示される

#### F-07: 連続二度寝記録
- **説明**: 連続日数のカウントと表示
- **受入基準**:
  - 毎日スヌーズを押すと連続日数が増加
  - 1 日でもスヌーズしないと連続記録がリセット
  - 連続日数が画面に表示される

#### F-08: デモ用ライブモード
- **説明**: 任意のタイミングでアラーム発火を再現できる（審査員向け）
- **受入基準**:
  - 設定画面に「デモ起動」ボタンがある
  - ボタンを押すと 5 秒後にアラームが発火
  - デモ用の履歴データが事前に仕込まれている

### 1.2 Nice-to-have 機能（時間があれば）

#### N-01: 季節・天気連動メッセージ
- 当日の日付・天気を Bedrock のプロンプトに渡し、文脈を反映

#### N-02: 称号システム
- 段階別の称号付与（見習い → 布団仙人 → 夢の住人）

#### N-03: 30 日卒業証書
- 和紙風の証書を生成・表示

#### N-04: 音声読み上げ
- Amazon Polly で AI メッセージを和テイストの声で再生

#### N-05: 季節背景画像
- Nova Canvas で事前生成した墨絵風背景を時間帯・季節で差し替え

#### N-06: 雨音 BGM
- アラーム鳴動時に環境音を流す（フリー素材）

#### N-07: 全国ランキング
- 連続二度寝記録の匿名ランキング

#### N-08: メッセージ履歴
- 過去に表示されたメッセージの一覧ページ

### 1.3 スコープ外

- 実機のスマホアラーム連携（ハッカソン後のモバイル版で対応）
- 複数アラームの設定
- ユーザー登録機能
- 課金・広告
- パターン C（昔話・故事系）のメッセージ

## 2. 非機能要件

### 2.1 パフォーマンス
- **AI メッセージ生成**: レスポンスタイム 5 秒以内
- **アラーム鳴動**: 設定時刻から 1 秒以内に発火
- **UI レスポンス**: ボタン押下から画面遷移まで 1 秒以内

### 2.2 コスト
- **ハッカソン期間（〜30 日）の合計コスト**: $1 以下を目標
- **開発時**: Amazon Nova Lite を使用
- **本番デモ時**: Claude Haiku または Claude Sonnet にスイッチ
- **トークン制限**: `max_tokens: 200` を全リクエストで明示
- **キャッシュ戦略**: 開発中はメッセージをローカルキャッシュし、再生成を最小化

### 2.3 セキュリティ
- ユーザー登録なし、個人情報の収集なし
- API キーや認証情報はクライアントに露出させない
- API Gateway + Lambda 経由で Bedrock 呼び出し
- HTTPS 通信の強制

### 2.4 ブラウザ対応
- Chrome / Safari の最新版で動作
- スマホ表示にも対応（レスポンシブデザイン）
- ハッカソン審査員のデモ環境を想定

### 2.5 可用性
- 初回ロード後はローカルストレージで最低限の機能（スヌーズ・記録）が動作
- オフライン時でも基本機能が利用可能

### 2.6 スケーラビリティ
- サーバレスアーキテクチャによる自動スケーリング
- DynamoDB のオンデマンドキャパシティ

### 2.7 保守性
- AWS サービスのマネージドサービスを活用
- Infrastructure as Code（CDK または CloudFormation）
- コードの可読性とドキュメント整備

## 3. ユーザーシナリオ

### 3.1 メインシナリオ：朝の二度寝体験

**前提条件**: ユーザーがアラームを設定済み

1. **前夜**: ユーザーがアプリで翌朝 7:00 のアラームを設定
2. **朝 7:00**: アラームが鳴る
3. **画面表示**: 雨音とともに墨絵風の画面が立ち上がる
4. **AI メッセージ**: 「春雨ですね。今朝の世界は、あなたを必要としていません」と表示
5. **ユーザー行動**: 巨大な「もう少し…」ボタンを押す
6. **記録更新**: 堕落ゲージ +1、連続二度寝記録が更新
7. **スヌーズ**: 10 分後に再度アラームが鳴る
8. **繰り返し**: 2〜3 回スヌーズを繰り返す
9. **起床**: 最終的に「起きる」ボタンを押して起床

**期待結果**: ユーザーが罪悪感なく二度寝を楽しみ、必要な睡眠を確保できる

### 3.2 サブシナリオ：30 日達成

**前提条件**: ユーザーが 29 日連続で二度寝を達成済み

1. **30 日目の朝**: アラームが鳴り、スヌーズを押す
2. **達成通知**: 「30 日連続達成！」のメッセージが表示
3. **卒業証書**: 和紙風の卒業証書が表示される
4. **内容**: 「あなたは立派に、朝起きられない人になりました」
5. **シェア**: スクリーンショットを撮って SNS にシェア

**期待結果**: ユーザーが達成感を得て、アプリの体験を共有したくなる

### 3.3 デモシナリオ：ハッカソン審査員向け

**前提条件**: デモ環境が準備済み

1. **イントロ**: 「あなたは、朝起きられますか？」の問いかけ
2. **アラーム設定**: デモ起動ボタンを押す
3. **5 秒待機**: カウントダウン表示
4. **アラーム発火**: 雨音と墨絵風 UI が表示
5. **AI メッセージ #1**: 詩的パターンのメッセージ
6. **スヌーズ**: 巨大ボタンを押す
7. **AI メッセージ #2**: 科学的根拠パターンのメッセージ
8. **記録表示**: 堕落ゲージ、連続 12 日目、称号「布団仙人」
9. **卒業証書**: 30 日達成版を表示
10. **締め**: 「スヌーズを押せ ── これは、押すべきボタンです」

**期待結果**: 90 秒で世界観・技術・社会貢献の三層を伝える

## 4. ビジネスコンテキスト

### 4.0 コンセプト（最重要）

本作は AWS Summit Japan 2026 AI-DLC ハッカソン
「人をダメにするサービスを考えよう」への提出作品である。

#### 三層構造

| 層 | 内容 |
|---|---|
| 表テーマ | 朝起きられない人を生産する（ダメな人を作る） |
| 体験の質感 | 風情あるアンチ効率の演出（雨音、墨絵、季語、待つ時間） |
| 裏のオチ | 効率化された朝への処方箋。睡眠不足社会の改善、自己肯定感の回復 |

#### 設計原則
- 「効率社会的にはダメ」かつ「人間性の観点では取り戻し」という両義性
- ブラックギャグの皮を被った社会的メッセージ
- 笑いと品の同居

### 4.1 解決する課題
- 日本の労働者の慢性的な睡眠不足
- 効率化文化による睡眠時間の削減
- 二度寝への罪悪感
- 自己肯定感の低下

### 4.2 ソリューションの価値
- 罪悪感なく必要な睡眠を確保できる
- 効率化社会への風情あるアンチテーゼ
- 自己肯定感の回復
- 睡眠の質の向上

### 4.3 成功指標
- ハッカソンでの審査員評価
- デモのインパクト（90 秒で世界観を伝える）
- SNS でのシェア数
- ハッカソン後の継続利用率

## 5. 技術コンテキスト

### 5.1 技術スタック
- **フロントエンド**: React / Next.js
- **ホスティング**: AWS Amplify Hosting または S3 + CloudFront
- **API**: Amazon API Gateway
- **バックエンド**: AWS Lambda
- **AI**: Amazon Bedrock（Nova Lite / Claude Haiku / Claude Sonnet）
- **データベース**: Amazon DynamoDB
- **画像生成**: Amazon Nova Canvas（事前生成）
- **音声合成**: Amazon Polly（Nice-to-have）

### 5.2 統合ポイント
- フロントエンド → API Gateway → Lambda → Bedrock
- フロントエンド → API Gateway → Lambda → DynamoDB
- フロントエンド → ローカルストレージ（オフライン対応）

### 5.3 データ要件
- **アラーム設定**: 時刻、有効/無効フラグ
- **スヌーズ記録**: 日付、回数、連続日数
- **メッセージ履歴**: メッセージ ID、パターン、テキスト、日時
- **ユーザー記録**: 堕落ゲージ、称号、累計時間

## 6. 品質属性

### 6.1 信頼性
- アラームが設定時刻に確実に鳴る
- スヌーズ記録が失われない
- AI メッセージ生成の失敗時のフォールバック

- 直感的な UI/UX
- 墨絵風の世界観が一貫している

### 6.3 テスト可能性
- デモ用ライブモードで任意のタイミングでテスト可能
- 各機能が独立してテスト可能

### 6.4 アクセシビリティ
- 基本的なアクセシビリティ対応（コントラスト、フォントサイズ）
- スクリーンリーダー対応は Nice-to-have

## 7. 制約条件

### 7.1 時間的制約
- ハッカソン期間内（24 時間想定）での開発
- デモは 90 秒以内

### 7.2 技術的制約
- AWS サービスのみを使用
- ブラウザの Web API に依存（通知、音声）
- ユーザー登録なし（ローカルストレージベース）

### 7.3 コスト制約
- ハッカソン期間の合計コスト $1 以下

### 7.4 倫理的制約
- 医療助言ではない旨の明示
- 重要な予定への寝坊リスクの警告
- 過度な使用への注意喚起

## 8. リスクと対策

### 8.1 技術リスク

| リスク | 影響 | 対策 |
|---|---|---|
| Bedrock API のレスポンス遅延 | ユーザー体験の低下 | タイムアウト設定、フォールバックメッセージ |
| ブラウザ通知の許可が得られない | アラームが機能しない | 許可を促す UI、代替手段の提示 |
| ローカルストレージの容量制限 | データ保存失敗 | データサイズの最適化、古いデータの削除 |

### 8.2 ビジネスリスク

| リスク | 影響 | 対策 |
|---|---|---|
| 重要な予定への寝坊 | ユーザーの信頼低下 | 「起きる」ボタンを必ず押せるようにする |
| 不謹慎な表現 | 審査員の評価低下 | プロンプト制約、出力レビュー |
| ハルシネーション | 科学的根拠の誤り | 既知の常識的な範囲に限定 |
